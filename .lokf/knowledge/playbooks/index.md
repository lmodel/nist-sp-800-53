# Playbooks

* [Regenerate and test after a schema change](regenerate-and-test.md) - How to change the schema and check it: `uv sync --group dev`, edit `src/nist_sp_800_53/schema/nist_sp_800_53.yaml`, then `just lint`, `just gen-project`, `just gen-doc`, `just lokf-adapt` and `just test`, and the pre-commit hooks before a pull request.
* [Validate data against the schema](validate-data.md) - How to validate SP 800-53 data with `linkml-validate` before loading it into the generated Python models, which check less: the dataclasses check no pattern, and the Pydantic models miss the identifier types' patterns. No check covers the nesting of identifiers, a repeated one, or what a withdrawn element carries.
* [Update the upstream pins](update-upstream-pins.md) - What to do when the weekly upstream watch reports that NIST registered the next final edition of SP 800-53, released a changed catalog or baseline in usnistgov/oscal-content, moved the pinned tag or folder, or that a copy drifted: replace the copies whole from one release, move the pins in `scripts/check_upstream_release.py` and the schema header, regenerate, and run the tests.
* [Cut a release](release.md) - How a release is made: Conventional Commits on `main`, an `## [Unreleased]` changelog section, the `v0.0.0` baseline tag that keeps the first release at 0.1.0, and `semantic-release.yml`, which tags the release and dispatches Knowledge Release to attach `schema-<tag>-nist-sp-800-53.yaml` once `KNOWLEDGE_RELEASE_ENABLED` is true.
* [Knowledge sources map](knowledge-sources.md) - The librarian's scrape map: every repository location and external page this bundle derives concepts from, the concepts each yields, how to re-check each on a refresh run, and the paths left out on purpose.
